01

Formulario de contacto — Web3Forms

El formulario de contacto anterior no tenía atributos name en sus campos, por lo que FormData no capturaba ningún dato. Se eliminó la dependencia de WhatsApp y EmailJS y se integró Web3Forms, que envía el mensaje directamente al correo del propietario sin requerir permisos OAuth.

📧

Integración Web3Forms

NUEVO

Se usa la API pública de Web3Forms. El cliente rellena el formulario y hace clic en "Enviar" — no tiene que hacer nada más. El correo llega al inbox del administrador en segundos.

ANTES — sin funcionar
<input placeholder="Tu nombre" />
<input placeholder="Correo" />
<!-- Sin name="" → FormData vacío -->
AHORA — operativo
<input name="nombre" />
<input name="correo" />
<input name="telefono" />
<textarea name="mensaje" />

La función submit ahora es async: deshabilita el botón mientras envía, muestra "Enviando…", solo marca éxito si la API confirma data.success === true y muestra error toast en caso contrario.

02

Checkout — pedido sin WhatsApp

El proceso de compra anterior abría WhatsApp del navegador y el cliente tenía que enviar el mensaje manualmente. Si no tenía sesión iniciada en WhatsApp Web, el proceso fallaba. Ahora el cliente solo hace clic en "Confirmar pedido" y el sistema hace todo.

🛒

Confirmación automática vía Web3Forms

CORREGIDO

Al confirmar, se envía el pedido completo (productos, cantidades, datos de envío, método de pago) al correo del administrador. El carrito solo se vacía si el envío es exitoso — si hay error de red, el cliente no pierde su pedido.

  • Botón deshabilitado durante el envío para evitar doble clic
  • Texto del botón cambia a "Enviando pedido…" mientras procesa
  • Pantalla de éxito muestra número de pedido y total
  • Toast de error si la API falla, sin borrar el carrito
  • Pedido guardado en localStorage / ff_orders para el dashboard del admin
  • Stock de cada producto decrementado automáticamente al confirmar
03

Errores de lógica corregidos

Se identificaron y resolvieron 10 puntos débiles que causaban comportamiento incorrecto, crashes silenciosos o experiencias de usuario confusas.

⚛️

Bug 1 — Hooks fuera de componente React

CRÍTICO

Todas las páginas con hooks (useState, useEffect) se llamaban como funciones ordinarias renderPage(). Esto viola las Reglas de Hooks de React y causaba crashes aleatorios y comportamiento impredecible de estado.

ANTES — incorrecto
case "contacto": return ContactPage(ctx);
AHORA — correcto
case "contacto": return <ContactPage ctx={ctx} />;

Todas las firmas de funciones de página cambiadas de (ctx) a ({ ctx }). Archivo afectado: pages.jsx + app.jsx

🗑️

Bug 2 — Items fantasma en el carrito

CORREGIDO

Si el admin cambiaba o eliminaba productos, el carrito del cliente podía contener IDs que ya no existían. Al ir al checkout, los items aparecían sin nombre, precio ni imagen.

Se añadió un useEffect al montar la app que filtra el carrito contra el índice activo de productos. Items inválidos se eliminan automáticamente. Archivo: app.jsx

🔍

Bug 3 — Doble render en el catálogo

CORREGIDO

El componente Catalog tenía un useEffect que sincronizaba cat con initialCat. Esto causaba un render extra innecesario cada vez que el usuario cambiaba de categoría.

Se eliminó el efecto redundante. El estado se inicializa directamente con useState(initialCat). Archivo: components-shop.jsx

🏎️

Bug 4 — IntersectionObserver antes del DOM

CORREGIDO

El observer de animaciones .reveal se registraba antes de que React pintara el DOM nuevo al cambiar de ruta. Muchos elementos nunca entraban en viewport y nunca se animaban.

Se añadió un setTimeout de 50ms para esperar el siguiente frame de pintura antes de registrar los elementos. Archivo: app.jsx

💬

Bug 5 — Disclaimer engañoso en reseñas

CORREGIDO

El formulario de reseñas decía "la publicamos pronto" dando a entender un proceso automático, cuando en realidad las reseñas requieren revisión manual del equipo.

Texto actualizado a: "La revisamos y, si todo está en orden, la publicamos manualmente." Archivo: pages.jsx

🚚

Bug 6 — Condición de envío gratis incorrecta

CORREGIDO

La condición de envío gratis incluía || subtotal === 0, lo que regalaba envío gratis cuando el carrito estaba vacío — una condición imposible de alcanzar en el checkout pero lógicamente incorrecta.

Simplificado a subtotal >= FREE_SHIP. Archivo: pages.jsx

🪟

Bug 7 — postMessage sin verificar iframe

CORREGIDO

El panel de tweaks llamaba window.parent.postMessage() incondicionalmente. Cuando la tienda cargaba directamente (sin estar dentro de un iframe), esto lanzaba errores de seguridad de cross-origin en consola.

Se añadió guardia if (window.parent !== window) antes de cada llamada. Archivo: tweaks-panel.jsx

💰

Bug 8 — Costo de envío hardcodeado

CORREGIDO

El valor de Q35 de envío estándar estaba escrito directamente en el código del checkout. El admin no podía cambiarlo sin modificar el código fuente.

Cambiado a const SHIP_COST = () => FF.SHIP_COST || 35 — se lee del objeto global que a su vez carga desde localStorage. El admin puede editarlo desde Ajustes. Archivo: pages.jsx

📝

Bug 9 — Inputs de contacto sin name

CRÍTICO

Los campos del formulario de contacto no tenían atributo name. FormData devolvía un objeto vacío, por lo que el mensaje llegaba sin ningún dato del cliente.

Añadidos name="nombre", name="correo", name="telefono", name="mensaje". Archivo: pages.jsx

💳

Bug 10 — Carrito se borraba aunque el pedido fallara

CRÍTICO

En el checkout original, clearCart() se llamaba antes de esperar la respuesta de la API. Si había un error de red, el cliente perdía su carrito sin que el pedido se hubiera procesado.

clearCart() movido dentro del bloque try, después de confirmar que data.success === true. Archivo: pages.jsx

04

Dashboard de ventas en el admin

Se añadió una nueva pestaña "Dashboard" que es la pantalla principal del admin. Usa Chart.js para visualizar los datos de pedidos guardados en ff_orders.

📊

KPI Cards — 4 métricas clave

NUEVO
  • Ingresos totales — suma de todos los pedidos en Q
  • Total de pedidos — cantidad y cuántos están pendientes
  • Ticket promedio — ingresos ÷ pedidos
  • Unidades vendidas — total de productos despachados
📈

Gráficas interactivas (Chart.js 4.4)

NUEVO
  • Barras de ingresos (30 días) — evolución diaria de ventas, con tooltip en Q
  • Dona por categoría — distribución de ventas: Proteínas, Creatina, Pre-entreno, Aminoácidos, Vitaminas
  • Top 5 productos — ranking con podio dorado, unidades vendidas y total en Q
  • Pedidos recientes — los últimos 5 pedidos con estado y total
⚠️

Estado vacío

DETALLE

Si no hay pedidos todavía, el dashboard muestra un estado guía en lugar de gráficas vacías. Los datos se generan en tiempo real a medida que llegan pedidos de la tienda.

05

Gestión de pedidos

Nueva pestaña "Pedidos" en el admin. Cada pedido confirmado desde la tienda se guarda automáticamente en localStorage / ff_orders y es visible aquí.

🛒

Lista de pedidos con filtros

NUEVO
  • Filtros por estado: Todos / Pendiente / Confirmado / Enviado / Entregado / Cancelado
  • Tabla con: # pedido, fecha/hora, cliente, departamento, productos, total, método de pago
  • Cambio de estado directo desde la tabla (select dropdown)
  • Expandir fila para ver detalle completo: dirección, teléfono, correo, referencia, desglose de productos
  • Botón de eliminar pedido del historial
📦

Flujo de estados

NUEVO
Pendiente → Confirmado → Enviado → Entregado

Cualquier pedido puede marcarse como Cancelado en cualquier momento. El cambio se guarda automáticamente en localStorage.

⚠️

Limitación importante

NOTA

Los pedidos se guardan en el localStorage del navegador donde se abre el admin. Si otro dispositivo o navegador abre el admin, no verá los mismos pedidos. Para sincronización multi-dispositivo se necesitaría un backend con base de datos. El sistema de email (Web3Forms) sí notifica al correo en todos los casos.

06

Inventario de productos

Se añadió el campo stock a todos los productos del catálogo y se integró en el panel de admin y en el proceso de checkout.

📦

Campo stock en cada producto

NUEVO
  • null = sin límite de stock (products digitales o con stock ilimitado)
  • Un número entero = cantidad disponible en inventario
  • Al confirmar un pedido, el stock se decrementa automáticamente
  • No puede bajar de 0
🔴

Indicadores visuales en la tabla de productos

NUEVO
48 uds. — Stock OK 12 uds. — Stock bajo (<15) 3 uds. — Crítico (<5) Sin límite

El admin puede editar el stock de cualquier producto desde el formulario de edición. Dejar el campo vacío = sin límite.

07

Configuración de envío desde el admin

Los costos de envío ahora son configurables desde el panel de administración, sin tocar código.

🚚

Dos parámetros editables desde Ajustes

NUEVO
  • Envío gratis desde (Q) — monto mínimo para envío gratis (default: Q400)
  • Costo de envío estándar (Q) — costo cuando no alcanza el mínimo (default: Q35)

Los valores se guardan en localStorage / ff_data y se leen cada vez que se carga la tienda. El checkout los usa automáticamente.
